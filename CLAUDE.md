# Working Big & Small (工作大小事)

Firebase project: `workplace-big-small`. Vite + TS frontend (`src/`), Cloud Functions v2 backend (`functions/`), Firestore.

## Deploy workflow (user-approved standing instruction)

After making a code change in this project:
1. Run the build check for whatever was touched (`npm run build` at repo root for frontend, `npm run build` in `functions/` for backend). Never commit/push/deploy on a failing build.
2. `git add` + `git commit` with a message describing the change, then `git push origin main`. Do this automatically without asking each time.
3. Run `firebase deploy` to publish to production. Do this automatically without asking each time.
4. Report what changed and the deploy result — auto-executing the mechanics doesn't mean skipping the summary, and anything risky/unfinished (e.g. missing secrets, WIP features) should still be flagged even though the push/deploy itself isn't gated on asking first.

## Environment gotchas (this machine)

- **`firebase deploy` must be run via the PowerShell tool, not Bash/Git-Bash.** In Git Bash, the functions discovery step (`Cannot determine backend specification. Timeout after 10000`) reliably times out because Git Bash's nested spawn of `cmd.exe` (used internally by `firebase-tools` for its `npm show` SDK-version check) is extremely slow/hangs in that shell — confirmed by reproducing the exact same `spawnSync cmd.exe ETIMEDOUT` outside of any Firebase code. Running the identical `firebase deploy` via PowerShell avoids this entirely and completes normally.
- **`feature/ecpay-migration` branch — DO NOT run `firebase deploy` (or any `--only functions`/`--only hosting` variant) against the `workplace-big-small` project from this branch without explicit, deliberate confirmation.** `main` is live in production on this exact same Firebase project (there is no separate staging project) with real PayPal payments active; this branch replaces every PayPal Cloud Function (`createTopupOrder`, `captureTopupOrder`, `paypalWebhook`, ...) with ECPay equivalents under the same function names, so deploying it would silently take down real production checkout. `paypal-stable` branch exists as the known-good PayPal snapshot to fall back to. Verification on this branch so far has deliberately avoided any deploy — see the Payment system section below for what's been checked and how.
- `functions/.env` (gitignored, see `.env.example` for the template) — `main`/`paypal-stable` need `PAYPAL_ENV=live` (the project went live 2026-08-01), this branch instead needs `ECPAY_ENV` (stage/production, see ecpayClient.ts). Since this file is gitignored, switching branches does NOT change its contents — check which var the checked-out branch's code actually reads before assuming it's set correctly, and never deploy `main` while this file only has an ECPay-branch value or vice versa; a non-interactive `firebase deploy` fails outright if the branch's required var has no value at all (Firebase can't prompt with no TTY attached), but silently deploying the WRONG value for that env var is worse than an outright failure — see the `main`-branch incident this bullet used to describe, where a stale "sandbox" default from `.env.example` silently flipped a live PayPal deploy back to sandbox and hung checkout for real customers.
- Firebase CLI login is shared across all shells on this machine (stored in the OS user profile, not per-terminal) — once logged in once anywhere, `firebase login:list` succeeds everywhere, including from an agent's sandboxed shell.
- This machine's default Node (via nvm-windows) was 18.16.0; this project's tooling (`firebase-tools`, `functions/package.json` engines) needs Node 20+. Node 22 is installed via `nvm install 22` / `nvm use 22`, plus a global `firebase-tools` install (`npm install -g firebase-tools`) so `firebase` works without `npx`. `nvm` itself must be run from a real PowerShell/CMD window (not Git Bash), or it refuses with a GUI dialog.

## Payment system status

**`main`/`paypal-stable` branches: PayPal, live in production.** `functions/src/paypalClient.ts`, `topupHandlers.ts`, `paypalWebhook.ts`, `refundService.ts`, `adminHandlers.ts`, `src/paypalTopup.ts`, `src/paypalSdk.ts`, `src/admin/*` implement a full PayPal top-up + admin dashboard (Stage 1-4 design, see comments in those files). **This project went LIVE on 2026-07-31 — real cards, real charges, not PayPal Sandbox anymore.** `PAYPAL_CLIENT_ID`/`PAYPAL_CLIENT_SECRET` in Firebase Secret Manager hold the Live app's credentials (currently secret version 4 for both — a stale/mismatched version was live-tested and rejected before, see git history around 2026-08-01), `PAYPAL_ENV` in `functions/.env` must be `live`, and `src/paypalSdk.ts`'s hardcoded `PAYPAL_CLIENT_ID` is the Live Client ID. All three must agree, or checkout hangs on the payment iframe. `PAYPAL_WEBHOOK_ID` is unchanged from setup and assumed still correct.

**`feature/ecpay-migration` branch: full PayPal→ECPay (綠界科技) rewrite, not yet deployed anywhere.** Chosen scope (see conversation this branch was created in): credit-card-one-time-payment only (`ChoosePayment=Credit`, no ATM/CVS/barcode), full replacement of PayPal (no dual-gateway option), ECPay's publicly documented stage test merchant (`MerchantID 2000132`) for now — real 特約商店 credentials TBD. Backend: `functions/src/ecpayClient.ts` (CheckMacValue signing — .NET-style URL-encoding quirk, see its own doc comments — plus checkout-param building and the credit-card refund API), `ecpayCallback.ts` (replaces `paypalWebhook.ts` — ECPay's ReturnURL notify is the *only* path to crediting an order, not a backup for a client-triggered capture the way PayPal's webhook was; must reply with the literal string `1|OK`). Frontend: `src/ecpayCheckout.ts` (replaces `paypalSdk.ts` — no SDK, just builds+submits a hidden form to redirect the buyer to ECPay's hosted checkout page) and `src/ecpayTopup.ts` (replaces `paypalTopup.ts`). Dropped PayPal's dispute/chargeback webhook automation entirely (`recordDispute`/`resolveDispute`/`handlePaypalInitiatedRefund`, removed from `refundService.ts`) — ECPay's ReturnURL notify has no equivalent push for refunds/chargebacks initiated outside this app, so a real chargeback now needs a manual admin action (`adminSetPaymentReview` + `adminAdjustCoins`). The admin dashboard's 爭議 (disputes) tab is left in place but will only ever show empty state on this branch.

Verification done so far, without ever deploying to the shared production project (see the deploy-safety bullet above): the CheckMacValue algorithm and the exact browser-side redirect technique in `ecpayCheckout.ts` were confirmed correct by POSTing a real signed request straight to ECPay's public stage server (`https://payment-stage.ecpay.com.tw/Cashier/AioCheckOut/V5`) and getting back ECPay's real checkout page with the correct order id/item/amount rendered. The inbound `ecpayCallback.ts` path (order crediting, CheckMacValue verification on the way in) has NOT been exercised end-to-end — that needs either the Firebase local emulator suite (functions+firestore, fully isolated from prod) or an eventual careful production deploy once real merchant credentials are ready.

Admin dashboard is served from `mk9x2qzp7f.html` (deliberately unguessable filename, not `admin.html`) — real access control is Firebase Auth + the `admins/{uid}` Firestore allowlist (see `firestore.rules`), the odd filename is just an extra layer against casual path-guessing.
